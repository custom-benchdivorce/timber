# YueAI Community Resource Hub

YueAI Community Resource Hub is a specialized technical resource aggregation and navigation platform designed for developers, researchers, and community managers who require curated access to community-driven tools, datasets, and operational resources. The project addresses the fragmentation of high-quality community resources by providing a centralized, version-controlled index that combines automated link validation with manual curation workflows.

The platform targets technical leads, open-source maintainers, and DevOps engineers who need reliable access to community engagement metrics, user activity analysis tools, and real-time resource update notifications. By structuring external links through a standardized metadata layer, the project enables users to track resource availability, categorize assets by functional domains, and maintain historical change logs without depending on proprietary services.

## 功能概览

- **Automated Link Health Monitoring** – Periodically checks all registered external URLs for HTTP status code changes, TLS certificate validity, and DNS resolution consistency, generating alert reports for stale or migrated endpoints.

- **Metadata Tagging Engine** – Supports hierarchical classification (primary category, subcategory, usage type, region, language) with inheritance rules for batch updates across resource groups.

- **Community Activity Score Integration** – Aggregates public engagement signals (repository stars, forum thread counts, response latency percentiles) from linked community platforms to surface trending resources.

- **Custom Feed Builder** – Allows users to define filter rules based on tags, update frequency, or maintainer reputation, producing personalized JSON/Atom feeds for CI/CD pipelines or internal dashboards.

- **Audit Trail with Versioning** – Maintains immutable append-only logs for every resource addition, removal, metadata change, and status transition, supporting rollback and forensic analysis.

- **Bulk Import/Export Interface** – Provides CSV and YAML serialization formats for batch resource registration, offline editing, and cross-instance synchronization via Git repositories.

- **Slack/Telegram Notification Adapter** – Delivers real-time alerts for critical resource changes (downtime, content modification, domain expiration) through configurable webhook endpoints.

- **RESTful API with HMAC Authentication** – Exposes all core operations (list, search, create, update, delete, validate) through a versioned API with rate limiting and request signing for automated clients.

## 应用场景

- **Multi-community Operations Dashboard** – Operations teams managing concurrent user groups across different geographic regions use the hub to monitor the availability of regional registration portals and activity reporting endpoints, ensuring consistent access for local moderators without manual bookmark maintenance.

- **Automated Documentation Synchronization** – Technical writers integrate the resource hub into their documentation build pipeline to automatically fetch the latest community event URLs and training material links, reducing broken references in release notes and user manuals published across multiple distribution channels.

- **Compliance Audit Preparation** – Legal and compliance officers leverage the versioned audit trail to generate historical reports showing which external platforms were referenced during specific quarters, including timestamps of first use and last verification, streamlining due diligence processes for regulatory submissions.

- **Third-party Integration Testing** – Quality assurance teams configure the hub as a dynamic test data source for end-to-end suites, where each test run validates application behavior against the current set of community endpoints, catching API contract drifts and SSL misconfigurations before production deployment.

- **Community Resource Migration Planning** – When transitioning between collaboration platforms (e.g., forum software upgrades or migrating from self-hosted to cloud solutions), architects use the hub to inventory all current external links, segment them by dependency criticality, and schedule phased cutovers with minimized user impact.

## 快速开始

```bash
# Clone the repository from the official mirror
git clone https://github.com/yueai-community/resource-hub.git
cd resource-hub

# Install dependencies with pinned versions
pip install --no-cache-dir -r requirements.txt
python setup.py build_ext --inplace

# Initialize the local SQLite database and load seed resources
python manage.py migrate --check
python manage.py seed --source data/initial_resources.yaml

# Start the development server with live reload
python manage.py runserver --host 0.0.0.0 --port 8080 --debug
```

The server listens on all interfaces by default. Access the administrative interface at `/admin` with the default credentials (admin / changeme) and change the password immediately upon first login. The API root is available at `/api/v1/` with Swagger documentation at `/api/v1/docs/`.

## 贡献指南

1. **Fork and Branch Strategy** – Fork the main repository to your personal account, then create a feature branch with a descriptive name (e.g., `feat/add-webrtc-validation` or `fix/audit-log-race`). Never commit directly to the `main` or `develop` branches. Keep your branch rebased on the latest upstream `main` to minimize merge conflicts.

2. **Development Environment Setup** – Run `make dev-setup` to install all required tools (golangci-lint, migrate, swag, pre-commit). This command also configures the local SQLite database with test data and starts a Redis container via Docker. Verify your setup by executing `make test` – all unit and integration tests should pass within 90 seconds.

3. **Coding Standards and Linting** – All Go code must pass `golangci-lint run --config .golangci.yaml` with zero warnings. Use `go fmt` and `go vet` before each commit. For frontend changes (Vue components), run `npm run lint` and `npm run format` to enforce ESLint and Prettier rules. Commit messages must follow the Conventional Commits specification (feat, fix, docs, style, refactor, perf, test, chore) with a scope prefix when applicable.

4. **Testing Requirements** – Every new feature or bug fix must include corresponding test coverage. Unit tests should mock external dependencies (HTTP clients, Redis, filesystem). Integration tests must use the dedicated test database (separate from development). Aim for at least 85% overall code coverage; the CI pipeline blocks merges below 80%. Run `make coverage` to generate an HTML report.

5. **Pull Request Lifecycle** – Open a pull request against the `develop` branch with a clear description of the change, referencing any related issues (e.g., "Closes #42"). The PR template must be filled completely, including a checklist for documentation updates, migration notes, and manual testing steps. At least two maintainers must approve the PR, and all CI checks (build, test, lint, security scan) must pass before merging. After approval, the PR author is responsible for squashing commits into logical units and rebasing onto the latest `develop` before the merge is performed.

## 常见问题

**Q: How does the hub handle resources that become permanently unavailable or return 404 errors?**

The health check worker performs three consecutive probes with exponential backoff (1s, 2s, 4s) before marking a resource as "unhealthy". After 7 consecutive failures, the resource status transitions to "deprecated" and is excluded from default feed generation. Maintainers receive a weekly digest email summarizing all deprecated entries. Additionally, the audit log records each failure event, allowing users to trace when a link first started failing. For resources that are expected to be temporarily unavailable (e.g., scheduled maintenance windows), users can manually set a "suspended" status with an expiry time, after which the normal health check resumes automatically.

**Q: Can I run the resource hub entirely offline without internet access to the external links?**

Yes, the core platform (database, API, admin UI, feed generation) operates fully offline. The only feature that requires external connectivity is the health check worker, which periodically probes the registered URLs. If you disable the worker (by setting `WORKER_ENABLED=false` in the configuration), the hub functions as a static metadata catalog with manual update capabilities. All external link data is stored locally, and you can use the import/export interfaces to synchronize with other instances without contacting the original endpoints. This design is particularly useful for air-gapped environments or internal corporate networks where external access is restricted.

**Q: How are conflicts resolved when two administrators update the same resource metadata simultaneously?**

The API employs an optimistic locking mechanism using a version field (integer) that increments on every successful update. When a client submits an update, it must include the current version number from the last known resource state. If the version in the database differs (indicating a concurrent modification), the API returns a 409 Conflict response with the latest version and the conflicting fields. Clients are expected to re-fetch the current state, merge their changes, and retry with the updated version. This approach avoids distributed locks and works well for the typical low-write-traffic scenario of resource catalogs, maintaining high availability even under moderate concurrency.
